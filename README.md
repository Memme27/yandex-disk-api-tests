# Автотесты REST API Яндекс Диска

Проект автоматизированных тестов для [REST API Яндекс Диска](https://yandex.ru/dev/disk/rest/).
Покрыты методы **GET, POST, PUT, DELETE**, а также негативные сценарии —
авторизация и валидация параметров.

**Стек:** Python 3.10+, pytest, requests.

---

## Запуск

```bash
git clone <ссылка-на-репозиторий>
cd yandex-disk-api-tests

python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

export YANDEX_DISK_TOKEN="ваш_токен"   # Windows: set YANDEX_DISK_TOKEN=...
pytest
```

### Токен

Токен выдаётся на [полигоне Яндекс Диска](https://yandex.ru/dev/disk/poligon/).
Личная учётная запись не используется — тесты создают и удаляют папки, и это
должен быть отдельный тестовый аккаунт.

Токен читается только из переменной окружения `YANDEX_DISK_TOKEN` и нигде
не сохраняется. Если переменная не задана, тесты **пропускаются**, а не падают:
отсутствие настройки — это не дефект продукта, и красный прогон здесь вводил бы
в заблуждение.

### Выборочный запуск

```bash
pytest -m get          # только GET
pytest -m "put or post"
pytest -m negative     # авторизация и валидация
pytest tests/test_delete.py::TestTrash
```

## Что покрыто

| Метод | Эндпоинт | Проверки |
|---|---|---|
| GET | `/v1/disk` | код 200, поля квоты и их типы, `used_space ≤ total_space`, фильтр `fields` |
| GET | `/v1/disk/resources` | метаданные папки и файла, пустая папка, параметр `limit`, 404 на несуществующем |
| GET | `/v1/disk/resources/download` | ссылка на скачивание |
| PUT | `/v1/disk/resources` | 201 и Link в ответе, чтение после создания, вложенность, 409 на дубликате, имена с кириллицей и пробелами |
| PUT | upload-ссылка | загрузка файла, совпадение размера, 409 без `overwrite` |
| PUT | `/v1/disk/resources/publish` | 200, появление `public_url`, снятие публикации |
| POST | `/v1/disk/resources/copy` | 201, сохранность оригинала, размер копии, 409, `overwrite`, 404 на несуществующем источнике |
| POST | `/v1/disk/resources/move` | исчезновение источника, переименование |
| DELETE | `/v1/disk/resources` | 204 для пустой папки и файла, 202 для непустой, 404 на несуществующем, поведение при повторном удалении |
| DELETE | Корзина | `permanently=false` кладёт в Корзину, `permanently=true` минует её |
| — | негативные | 401 на всех эндпоинтах, 400 без `path`, 400 на неверном `sort`, ранняя ошибка на пустом токене |

## Принятые решения

**Клиент отделён от тестов.** `DiskClient` знает про базовый URL, заголовок
авторизации и таймауты; в нём нет ни одного `assert`. Проверки живут только
в тестах. Если смешать, при падении непонятно, что сломалось — запрос или
ожидание. Плюс при смене эндпоинта правится одно место, а не тридцать.

**Методы возвращают `Response`, а не распакованный JSON.** Тесту обычно нужен
и статус-код, и тело; у 204 тела нет вовсе. Распаковка на стороне клиента
скрыла бы код ответа — а для API-тестов он и есть главный предмет проверки.

**Уникальные имена.** Каждая папка называется `autotest_<8 hex>`. Прогоны
не конфликтуют друг с другом, можно запускать параллельно, и мусор от упавшего
теста не ломает следующий запуск.

**Уборка через `yield`.** Teardown в фикстуре выполняется, даже если тест упал.
Ошибки удаления в нём намеренно не проверяются: второе исключение из фикстуры
заслонило бы настоящую причину падения.

**Проверка результата, а не только кода ответа.** 201 означает, что запрос
принят, а не что ресурс появился. Поэтому за созданием почти везде идёт чтение:
тест утверждает, что папка действительно существует и имеет тип `dir`.

**Негативные сценарии отдельно.** Они проверяют не конкретный метод, а
поведение сервиса на некорректном входе, и группируются по этому признаку,
а не по HTTP-глаголу.

**Параметры передаются через `params=`, а не склейкой строки.** В путях Диска
регулярно встречаются пробелы и кириллица; кодирование отдано requests.
Отдельный тест проверяет именно такие имена — там кодирование и ломается.

## Известные ограничения

Тесты идут против живого API, поэтому:

- прогон зависит от доступности сервиса и сетевых таймаутов;
- при частых запусках можно упереться в ограничение частоты запросов (429);
- удаление непустых папок асинхронное — тест проверяет факт запуска операции
  (код 202 и ссылка), но не дожидается её завершения.
- параметр `sort` с нераспознанным значением не приводит к ошибке 400,
  как можно ожидать из документации: API игнорирует его и возвращает 200.
  Тест `test_invalid_sort_field_is_ignored` фиксирует фактическое поведение.
- на только что созданном аккаунте Диск не инициализирован, и API отвечает
  403 `DiskUnsupportedUserAccountTypeError` на любой запрос. Нужно один раз
  зайти на disk.yandex.ru под тестовым аккаунтом — после этого API работает.

Возможные следующие шаги: опрос статуса асинхронных операций, отчёты Allure,
параллельный запуск через `pytest-xdist`, прогон в GitHub Actions.
